## 2. NEW · F-12 · A no-group role-1 user can read HR personal data from the approval queue

**This is the most serious thing found across either run.**

F-7's fix guarded `workitem_store.list_items`. `/api/work/list` draws from **four** sources, and the
other two carry the identical "unassigned means everyone" pattern **with no role floor**:

`readthrough.workflow_pending(user_id)` —
```sql
OR assigned_to_type = 'unassigned'
OR assigned_to_type IS NULL          -- unconditional
```

`readthrough.automation_pending(user_id, group_ids)` —
```python
visible = (at is None                                  # unconditional
           or (at == "user"  and aid == int(user_id))
           or (at == "group" and aid in (group_ids or [])))
```

Verified: `ru_alex`, `ru_casey` and `ru_drew` return **byte-identical sets** of 74 workflow items and
3 automation items — across different groups, and including `ru_drew`, who **belongs to no group at
all**.

The workflow rows are benign here (74 identical test fixtures, generic summary, empty payload). **The
automation rows are not.** One item, read from `ru_drew`'s seat:

```
title  : Dayforce exception — NH07_hire_multiple_matches.pdf (emp 3149231)
summary: Multiple master records (2) for employee 3149231: Marcus Delgado; Marco Delgado
payload: {"automation_name": "dayforce-doc-upload", "kind": "review",
          "attachments": [{"name": "NH07_hire_multiple_matches.pdf",
                           "relpath": "exceptions/NH07_hire_multiple_matches.pdf", ...}]}
```

An employee number, two employee names, and a reference to their new-hire document — readable by any
authenticated account regardless of group.

**Severity: S1 candidate.** Caveats stated honestly: it requires an authenticated account (not
anonymous), and this is POC data from the Dayforce trial rather than a customer's. But the mechanism
is a real ACL failure, and on a customer install the content is whatever their automations put into
approval titles and summaries. I did **not** test whether the referenced attachment is itself
fetchable by that seat — that should be checked and is not claimed here.

**Same root cause class as F-7**: a shared "anyone can pick this up" pool whose implicit audience was
Developer+ only because the front door used to guarantee it. F-7's fix restored that floor in one of
the sources; the other two were not touched.

## F-12 · FIXED · verified on both UI-reachable paths

The fix is well built: `role` is **required keyword-only**, so a caller that forgets it gets a
`TypeError` rather than the pool; a missing or zero role **fails closed**; the guard sits inside both
functions so every caller inherits it; and results are re-filtered on the way back, so an older main
app that ignores `role` cannot reopen the hole.

**Both UI paths verified, not just the endpoint:**

Developer+ and admin counts are unchanged, so nothing was over-restricted.

## On the UI-vs-API scope decision

Worth stating plainly so it isn't mis-assumed later: **`/api/work/list` is not an API-only surface —
it is what the My Work UI calls.** There was never a UI/API split for the work queue; anything
leaking there leaked in the UI too. The fix landed server-side, so both are closed.

The one item I flagged but never tested — whether an automation approval's attachment `relpath` is
fetchable by a non-owner — is now **genuinely API-only residue**, for two independent reasons:
The Agent's My Work UI renders automation attachments as **names only, with no download control**;
and role 1 can no longer see those items at all, so the relpath cannot be obtained through the
product. Deferring it is well-founded. It remains **untested**, and is not claimed either way.
